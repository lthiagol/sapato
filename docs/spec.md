# Sapato — Spec

**S**kills **A**dministration, **P**ackaging & **A**gent **T**ool **O**rganization.

Sapato manages a portable *skill vault* (a plain folder) and installs skills from it into coding agents' skill directories. It is a Go CLI with a Bubble Tea TUI on top. Every TUI action maps to a CLI command.

## 1. Concepts

- **Skill**: a folder containing `SKILL.md` (Agent Skills format) plus optional files (`scripts/`, `references/`, `assets/`, …).
- **Vault**: the folder holding the user's skills. Source of truth. Portable: no machine-specific state inside it.
- **Agent / target**: an agent's user-level skills directory. Sapato copies skills into it.
- **Managed skill**: a skill in a target that Sapato installed (recorded in the target's lock file).

## 2. Config — `~/.config/sapato/config.toml`

Override the path with the global `--config <path>` flag. No env vars.

```toml
vault = "~/sapato-vault"        # default if omitted

[ui]
theme = "catppuccin-mocha"      # see §9.5; default catppuccin-mocha
icons = "nerd"                  # nerd | unicode | ascii; default nerd

[agents]                        # name = path; order here = order in the UI
claude   = "~/.claude/skills"
cursor   = "~/.cursor/skills"
pi       = "~/.pi/agent/skills"
opencode = "~/.config/opencode/skills"
agents   = "~/.agents/skills"
# codex  = "~/.codex/skills"                                       # commented = not managed
# work   = { path = "~/work/.claude/skills", reads = ["~/.agents/skills"] }
```

- **Agents are data.** Every agent uses the same placement (`<path>/<skill>/…` + `.sapato-lock.json`); supporting a new agent is one line. An agent is *configured* iff it has a line in `[agents]`; there is no `enabled` flag — comment or remove the line to stop managing it (sapato then no longer sees its installs).
- Value is a path string, or an inline table `{ path = "...", reads = ["..."] }` where `reads` lists extra dirs that agent also reads (used by `doctor` overlap checks).
- Names match `^[a-z][a-z0-9-]{0,31}$`. Order = order of the lines in the file (must be preserved when parsing). Two agents may not share a path (after `~` expansion and Clean).
- **No `[agents]` table (or no config file)** → the built-in defaults below, in that order. A present `[agents]` table is authoritative; an empty one means no agents.
- The old per-agent form (`[agents.claude]` with `path`/`enabled`) is rejected with an error explaining the new form.
- **No config file**: CLI commands run on defaults and never write a config (only `sapato config init` does). The TUI asks once at launch, as a modal confirm, `No config found. Create <path>?`; `y` writes the same file as `config init`, `n` continues on defaults for this run. Then, if the configured vault does not exist (no `sapato.toml`), the TUI asks `No vault at <path>. Create it?` (modal confirm); `y` runs the same code as `sapato init`, `n` exits with `no vault at <path>; run sapato init` (exit 1). The TUI never crashes on a missing vault.
- The global `--icons` and `--theme` flags override `[ui]` for one run. Unknown theme or icon set → error listing the valid names.
- `~` is expanded to the user home dir in every path.

### 2.1 Default config text

`config default`, `config init` and the TUI's first-launch prompt all write this exact text (one generator). Order: `vault`, `[agents]`, `[ui]` (`icons` before `theme`). Each key gets a comment block above it: what it does, the allowed values, the default. The `[agents]` lines are the built-ins with their `reads` as end-of-line comments. The icon and theme lists are generated from the code (theme family order, `(light)` and `(default)` marks), never hand-written. It must load to exactly the defaults.

```toml
# Sapato config. Generated by `sapato config default`.

# Folder holding your skill vault (sapato.toml + skills/). `~` is expanded.
# Default: ~/sapato-vault
vault = "~/sapato-vault"

# The skill folders, per harness, that sapato manages.
# Order here = order in the UI. Comment a line out to stop managing it.
# No [agents] table = the built-in defaults below; an empty table = no agents.
# Names: lowercase letters, digits and -, starting with a letter.
# Example:
#   name = "path"
#   name = { path = "path", reads = ["other dir this harness also reads"] }
# `reads` is only used by `sapato doctor` to spot skills visible twice.
[agents]
claude   = "~/.claude/skills"
cursor   = "~/.cursor/skills"            # also reads ~/.claude/skills
pi       = "~/.pi/agent/skills"          # also reads ~/.agents/skills
opencode = "~/.config/opencode/skills"   # also reads ~/.claude/skills, ~/.agents/skills
agents   = "~/.agents/skills"
# codex  = "~/.codex/skills"
# work   = { path = "~/work/.claude/skills", reads = ["~/.agents/skills"] }

[ui]
# Icon set:
#   - nerd     Nerd Font glyphs (needs a Nerd Font in your terminal)
#   - unicode  plain Unicode symbols
#   - ascii    letters only
# Default: nerd
icons = "nerd"

# Color theme:
#   - catppuccin-latte (light)
#   - catppuccin-frappe
#   - catppuccin-macchiato
#   - catppuccin-mocha (default)
#   - dracula
#   - dracula-alucard (light)
#   - nord
#   - nord-light (light)
theme = "catppuccin-mocha"

# Skill assignments and per-skill compatibility live in the vault's sapato.toml.
```

The `reads` comments' column alignment is computed: each comment starts 3 spaces after the end of the longest agent line.

### Built-in defaults

| name       | path                          | also reads (for `doctor`) |
|------------|-------------------------------|---------------------------|
| `claude`   | `~/.claude/skills`            | |
| `cursor`   | `~/.cursor/skills`            | `~/.claude/skills` |
| `pi`       | `~/.pi/agent/skills`          | `~/.agents/skills` |
| `opencode` | `~/.config/opencode/skills`   | `~/.claude/skills`, `~/.agents/skills` |
| `agents`   | `~/.agents/skills`            | |

A configured agent named like a built-in, written as a plain string, inherits that built-in's `reads`; an inline table's `reads` replaces it.

## 3. Vault format

```
<vault>/
  sapato.toml
  skills/
    <name>/
      SKILL.md
      ...
```

`sapato.toml`:

```toml
format = 1                      # required, integer; only 1 is supported

[assignments]                   # optional; desired state used by `sync`
claude = ["code-review", "obsidian-*"]   # skill names or globs (path.Match)
agents = ["*"]

[skills.code-review]            # optional; vault-side metadata for one skill, never written into SKILL.md
compatible = ["claude"]         # agent names this skill works with; absent = compatible with every agent
```

### 3.1 New-vault manifest

`vault.Init` (used by `sapato init` and the TUI's create-vault prompt) writes exactly:

```toml
# Sapato vault manifest. Portable: no machine-specific paths here.

# Vault format version. Only 1 is supported.
format = 1

# Desired installs, applied by `sapato sync`.
# One line per agent name from your config's [agents]; values are skill
# names or globs (* ? [a-z]). Agents not configured on a machine are skipped there.
# `sync --prune` also uninstalls managed skills no longer listed.
# Example:
#   claude = ["code-review", "obsidian-*"]
#   agents = ["*"]
[assignments]

# Per-skill metadata, written by sapato (`sapato compat`, the TUI `c` key,
# the NEW wizard). You can edit it by hand too.
# compatible: agent names this skill works with; no table = every agent.
# Example:
#   [skills.code-review]
#   compatible = ["claude"]
```

An empty `[assignments]` is valid (sync does nothing).

### Compatibility

- A skill is compatible with every agent unless `sapato.toml` has `[skills.<name>] compatible = [...]`. An empty list is rejected on load (use the `remove` path instead: no entry = all).
- Names in `compatible` match the agent name pattern (§2). They need not be configured on this machine (the vault is portable); `doctor` reports unknown ones as info.
- sapato writes this table itself (`compat`, `remove`, imports with a manifest, the NEW wizard). A write edits only the lines of that skill's `[skills.<name>]` table: the old table (its header through its last key/value line; blank and comment lines after that, which may belong to the next table, are kept) is removed, and the new one, if any, is appended at the end of the file. Every other byte of the file (comments, `[assignments]`, other skills) is kept. Writes are atomic (temp file + rename). Unknown keys inside `[skills.<name>]` are rejected on load.
- `remove` deletes the skill's table. Removing the last compatible agent is not possible: setting compatibility to all agents deletes the table.

### Validation rules (a skill failing any rule is *invalid*)

1. `skills/<name>/SKILL.md` exists and is a regular file.
2. `SKILL.md` starts with YAML frontmatter delimited by `---` lines.
3. Frontmatter has non-empty `name` and `description` strings.
4. `name` equals the folder name.
5. `name` matches `^[a-z0-9]+(-[a-z0-9]+)*$`, max 64 chars.
6. `description` max 1024 chars.
7. Optional `metadata.version` (string). Display only.

Entries in `skills/` that are not directories, or start with `.`, are ignored.

## 4. Content hash

`sha256` over the skill folder, deterministic:

- Walk all regular files, skip any path component starting with `.` (e.g. `.git`, `.DS_Store`) and skip symlinks.
- Sort by slash-separated relative path.
- For each file feed: `relpath + "\n" + ("x" if any exec bit else "-") + "\n" + <len as decimal> + "\n" + content`.
- Result string: `sha256:<hex>`.

## 5. Lock file — `<target>/.sapato-lock.json`

```json
{
  "version": 1,
  "skills": {
    "code-review": {
      "hash": "sha256:…",
      "version": "1.2.0",
      "installed_at": "2026-11-21T13:00:00Z"
    }
  }
}
```

Missing file = empty lock. Writes are atomic (write temp file in same dir, rename). Lock is only written when it changes.

## 6. Status

For each (skill, agent) pair, over the union of vault skills and target dirs:

| status       | meaning |
|--------------|---------|
| `not-installed` | in vault (valid), not in target |
| `invalid`    | in vault but fails validation, not in target |
| `synced`     | in lock, target hash == lock hash == vault hash |
| `outdated`   | in lock, target hash == lock hash, vault hash differs |
| `modified`   | in lock, target hash != lock hash (local edits in target) |
| `orphaned`   | in lock, present in target, absent from vault |
| `unmanaged`  | in target, not in lock |
| `missing`    | in lock, folder gone from target |

| `incompatible` | in vault, not in target, and the skill is not compatible with this agent (§3) — replaces `not-installed` and `invalid` for that pair |

`modified` takes precedence over `outdated`. Target subdirs starting with `.` are ignored. Every status row also carries `compatible` (bool; `--json` includes it): an installed copy in an incompatible agent keeps its normal status with `compatible: false`.

## 7. Commands

Global flags: `--config`, `--dry-run` (on mutating commands: print plan, change nothing).
Agent selection: `-a/--agent <id>` repeatable, or `--all` (all configured agents). Skill args accept globs.

Glob vs literal: a skill named literally that hits a hard refusal (invalid on install, unmanaged on uninstall) fails the whole call. A skill matched only by a glob in that situation is skipped and reported (`skip <skill> in <agent>: <reason>`). Refusals that `--force` can override (modified; unmanaged on install) always fail the call without `--force`, glob or not. Errors read `<skill> in <agent>: <status>`.

| command | behavior |
|---------|----------|
| `sapato config` | print resolved config (vault, theme, icons, then agents in order with path and reads; notes when defaults are used because no `[agents]` table/config exists) |
| `sapato config default` | print the full commented default config (§2.1) to stdout. Writes nothing |
| `sapato config init` | write the §2.1 config to the `--config` path (default `~/.config/sapato/config.toml`), creating parent dirs; refuses if the file exists unless `--force`; `--dry-run` prints it instead (same text as `config default`) |
| `sapato init [path]` | create a vault (`sapato.toml` + `skills/`) at path or configured vault, writing the commented manifest of §3.1; fail if `sapato.toml` exists |
| `sapato list` | list vault skills: name, version, hash (short), valid/invalid + reason |
| `sapato status [skill…] [-a …]` | table of skill × agent status; `--json` |
| `sapato install <skill…> -a …` | copy vault skill to target; record lock. Refuses if target folder exists and is `unmanaged` or `modified` unless `--force`. Refuses an agent the skill is not compatible with (§3) unless `--force` (`<skill> in <agent>: incompatible`); with `--all`, or a glob, incompatible pairs are skipped and reported instead. Invalid skills are never installed |
| `sapato compat <skill> [agent…]` | no agents: print the skill's compatibility (`all agents` or the list). With agents: set `compatible` to exactly that list. `--all`: compatible with every agent (deletes the table). Skill must be in the vault; agent names must match the name pattern; `--dry-run` prints the change |
| `sapato guide [--install]` | print a generated `SKILL.md` (frontmatter `name: sapato`) that teaches an agent how to write skills for this vault: the resolved vault path, the folder layout, the validation rules (§3), compatibility metadata and the `compat` command, how to create (`new --name`, `new <file>`), import, install and check (`list`, `status`, `doctor`), and the configured agents in order. `--install` writes it as the vault skill `sapato` (refuses if `skills/sapato` exists with different content unless `--force`; identical content is a no-op). Never writes outside the vault |
| `sapato uninstall <skill…> -a …` | remove managed skill folder + lock entry. Refuses `unmanaged` (never delete what we don't own) and `modified` unless `--force` |
| `sapato update [skill…] [-a …]` | re-install every `outdated` skill (default: all skills, all agents). `modified` skipped unless `--force` (reported as skips, never call failures, even for literal names) |
| `sapato diff <skill> -a <id>` | unified diff vault vs installed copy (file list + per-file text diff) |
| `sapato import <source> [--name n]` | copy skills into the vault. Sources (§7.1): local folder, local `SKILL.md` file, git URL, raw `SKILL.md` URL, tarball (§11). Validates first; refuses if name exists unless `--force`. `--subdir`, `--all`, `--fix`, `--description` per §7.1 |
| `sapato new [file]` | create a vault skill from a complete `SKILL.md` (file or stdin). Name comes from frontmatter; must be valid; refuses an existing name unless `--force` |
| `sapato new --name n --description d [--compatible a,b] [--edit]` | scaffold mode: write `skills/<n>/SKILL.md` from the built-in template (§7.2) and, with `--compatible`, the compat table. Same validation and `--force` rule. `--edit` then opens it in `$VISUAL`, else `$EDITOR`, else `vi`. A file argument and `--name` together are a usage error |
| `sapato export <skill…> [-o file]` | write a tarball (§11). Default file: `<name>-<version or 8-char hash>.skill.tar.gz` for one skill, `skills-<date>.skill.tar.gz` for several. Invalid skills refused |
| `sapato adopt <skill…> -a <id>` | copy an `unmanaged` target skill into the vault, then record it in that target's lock (it becomes `synced`). Also records it in the lock of every other configured agent whose `unmanaged` copy of that name has the identical hash (they become `synced` too). Skill args accept globs over that agent's unmanaged skills |
| `sapato remove <skill>` | delete skill from vault and its `[skills.<name>]` table. Refuses if installed anywhere unless `--force` (installed copies become `orphaned`) |
| `sapato sync` | apply `[assignments]`: install/update assigned skills; uninstall managed skills no longer assigned (`--prune`, off by default) |
| `sapato doctor` | report: invalid vault skills, corrupt locks, duplicate exposure via read overlaps (same skill visible to one agent from two dirs), missing/orphaned/modified entries |
| `sapato tui` (also bare `sapato`) | interactive UI |

Notes: `remove` counts an agent as "installed" if status is synced/outdated/modified in any configured agent; `missing` does not count. `adopt --force` overwrites a same-named vault skill. `import` takes the skill name from frontmatter (`--name` must match it, unless `--fix` renames, §7.1).

`sync` rules: acts only on agents with an `[assignments]` key (others never pruned); assignments naming an agent not configured on this machine are reported as skips (`not configured here`) and never fail the sync; `doctor` lists them as info; literal/glob and refusal rules match install/update/uninstall; plans everything (dry-run) before applying. `--force`/`--prune` are CLI flags.

`doctor` severities: `error` = invalid vault skill, corrupt lock (exit 1); `warn` = modified, missing, orphaned, overlap; `info` = assignments naming an agent not configured here. Findings go to stdout.

Overlaps (§2) are about fixed directories the agent itself reads (e.g. cursor always reads `~/.claude/skills`, wherever sapato's `claude` target is configured). Resolve those extra-read dirs from the home dir, and compare each extra-read dir to that agent's own path (and to its other read dirs), symlinks resolved.

Compatibility in other commands: `A`/`--all` installs and `sync` skip incompatible pairs (`skip <skill> in <agent>: incompatible`; a literal assignment name is reported the same way and never fails the sync). `update` still updates an outdated copy in an incompatible agent (it is already there). `doctor`: `warn` for a managed copy installed in an incompatible agent; `info` for a `compatible` name not configured here; `info` when a skill installed in one agent's dir is read (via that agent's or another agent's `reads`, §2) by an agent it is not compatible with.

Exit codes: 0 ok, 1 error, 2 usage error. Errors go to stderr.

### 7.1 Import sources

The source kind is decided in this order:

1. Ends in `.tar.gz`/`.tgz` → tarball (§11). If its manifest has `compatible` for a skill, that is written to the vault's `[skills.<name>]` table on import. A manifest describes the full state: a skill it imports without a `compatible` entry has any existing table removed. Without a manifest, tables are left alone.
2. `https://` URL whose path ends in `.md` → **raw file**: HTTP GET (15s timeout, max 1 MiB body, status must be 200), treated as a one-file skill folder holding `SKILL.md`. A GitHub blob URL `https://github.com/<o>/<r>/blob/<ref>/<path>` is fetched from `https://raw.githubusercontent.com/<o>/<r>/<ref>/<path>`. Name hint (for `--fix`): the URL path's parent directory name; for a GitHub blob/raw URL whose file sits at the repo root, the repo name.
3. Other git URL (`https://`, `git@`, `*.git`) → shallow clone (as before).
4. Local path to a regular file ending in `.md` → **local file**, treated like a raw file. Name hint: its parent directory name. Any other regular file (not a tarball) is an error.
5. Local directory.

**Skill discovery** in a folder or clone: with `--subdir`, exactly that folder. Otherwise, if the root holds `SKILL.md`, the root is the skill. Otherwise every directory (depth ≤ 4, skipping dot-dirs and symlinks, not descending into a found skill) holding `SKILL.md` is a candidate: one candidate → that skill; several → error listing their relative paths unless `--all` (import every candidate, all-or-nothing, like a multi-skill tarball; `--name` not allowed); none → error. Name hint for a folder skill: its directory name (for a clone root, the repo name without `.git`).

Rule 4 of §3 is checked against the vault folder, which always takes the skill's (possibly repaired) name: a source folder named differently from its frontmatter `name` imports without `--fix`.

**`--fix`** (folder, file and raw sources; not tarballs): when a skill fails only frontmatter rules (2, 3, 5 of §3; `--name` differing from the frontmatter name also counts and renames the skill), sapato repairs the vault copy instead of refusing: the name becomes `--name` if given, else the frontmatter name if it passes rules 3 and 5, else the name hint normalized (lowercase; runs of characters outside `[a-z0-9]` become `-`; leading/trailing `-` trimmed; cut to 64); a missing or empty description takes `--description` (required in that case, else the error says so); missing frontmatter is created. Only the frontmatter's `name` and `description` keys are set; other keys, their order and the body are kept. The source is never modified. Problems `--fix` cannot repair (description too long, no `SKILL.md`) still refuse. Without `--fix`, an invalid skill is refused and the error suggests `--fix` when it would help.

### 7.2 New-skill template

`new --name` and the TUI wizard write this `SKILL.md` (the description YAML-quoted when needed):

```markdown
---
name: <name>
description: <description>
---

# <name>

<!-- One or two sentences: what this skill does. -->

## When to use

<!-- The situations that should trigger this skill. -->

## Steps

1. <!-- What the agent does, in order. -->

## Notes

<!-- Constraints, gotchas, files in this folder (scripts/, references/, assets/). -->
```

## 8. Install mechanics

- Copy into `<target>/.<name>.sapato-tmp`, then remove the old folder (if any) and rename into place. Then update lock.
- Preserve file mode bits. Skip symlinks and dot-paths (same rule as hashing).
- Create target dir if missing.

## 9. TUI (Bubble Tea)

All mutations go through `ops`, exactly like the CLI. Force-overridable refusals (`ops.ErrNeedsForce`, update skip `modified`) always get a distinct force confirmation; plain destructive ops get a plain confirmation.

### 9.1 Layout (every screen)

1. **Header**, centered: the ANSI Shadow `SAPATO` art (exact text in `internal/tui/art.go`, see task 10) in the theme accent, then the tagline `Skills Administration, Packaging & Agent Tool Organization` in subtext. If the terminal is shorter than 30 rows or narrower than the art, use a one-line header: `sapato · <tagline>` (tagline dropped if it doesn't fit).
2. **Rule** (full width, overlay color).
3. **Screen body** (below).
4. **Bottom bar**: a full-width rule carrying the summary, then 1 hint row (2 when it wraps). No background fill (it blends with the screen), no mode badge, no powerline glyphs.
   - Hint style everywhere: key in Accent (bold), description in Subtext, hints joined with ` · ` in Overlay.
   - **Rule with summary**: the rule (Overlay) holds the summary right-aligned, as ` N skills · N invalid · N need attention ` followed by `──` (2 rule glyphs) to the right edge; `N skills` in Text, the invalid part in Red and the attention part in Yellow, either dimmed to Overlay when 0. If the terminal is too narrow for the summary plus 4 rule glyphs, the parts drop from the right (attention, then invalid); if even `N skills` doesn't fit, the rule is plain.
   - **Hint row**, horizontally centered: the current screen's/mode's **action** hints, then ` │ ` (Overlay), then the **global** hints: `↑↓ move` (and `pgup/pgdn page` on the skill screen), `esc back` where it applies, `t theme`, `L log`, `? help`, `q quit`. Global hints are drawn one step dimmer (key in Subtext, description in Overlay). FILTER mode shows only `/ <query>` followed by `enter apply · esc clear`, and a confirm only `y yes · n no` (no `│`, no globals: those keys are typed text or cancel there).
   - **Fitting**: if the row is wider than the terminal, the globals move to a second row (also centered, no `│`). If the globals still don't fit, `t theme` then `L log` are dropped (`?` lists them). If the action part alone is too wide, it is truncated with `…`. The bar is therefore 2 or 3 lines tall; the body gets the rest.
   - The bar shows no action messages; those are notifications (§9.6).

### 9.2 Main screen (mode `MAIN`)

- Grid: a column-header row between two rules, then the skill rows in a scrolling viewport. Columns: `SKILL` (width = longest name, capped; overflow truncated with `…`), then one column per configured agent (width = max(len(id), 3) + 2; icon centered). The whole grid block is horizontally centered.
- Cursor is per row (skill). No column cursor. Selected row uses the surface color background and a `▶`/`>` marker.
- Status icon per cell (§9.5) colored by status. Empty cell (pair absent everywhere) = blank.
- Keys: `↑↓`/`jk` move, `g`/`G` top/bottom, `pgup`/`pgdn`, `enter` open skill screen, `/` filter (substring; `esc` clears), `r` refresh, `n` add a skill (ADD screen, §9.4), `t` theme picker; `a` (ADOPT) and `I` (IMPORT) still work as shortcuts but are not in the bar (listed in HELP), `?` help, `q` quit.
- Bar summary (in the bar's rule): `N skills · N invalid · N need attention` (attention = outdated + modified + orphaned + missing).

### 9.3 Skill screen (mode `SKILL`)

- Layout: two bordered panes (rounded border, Overlay color; the focused sidebar's border in Accent), filling the body width with a 1-col outer margin. Pane titles sit in the top border (` AGENTS `, ` <skill name> `).
- **Sidebar (left)**: width = widest agent row + borders, at least 26. One row per configured agent: mark (§9.5), cursor marker, agent id, status icon + short status word (`not inst.` for not-installed). Cursor per agent row. `space` toggles a mark; actions apply to marked rows, or to the cursor row if none marked.
- **Details (right)**, takes the remaining width; scrolls with `pgup`/`pgdn` if taller than the body:
  1. `version <v|->   hash <short>   <valid icon> valid|invalid`
  2. description, wrapped to the pane, max 3 lines (`…` when cut)
  3. `vault  <path>` (or `vault  not in vault` with the value dimmed); labels share one column width; each problem in red if invalid
  4. blank line, then the cursor agent's section, **always exactly 2 lines** so FILES never moves when the cursor changes agent: line 1 `<agent>  <icon> <status word as in the sidebar>` + ` · installed <YYYY-MM-DD HH:MM>` (local time) from the lock when managed + ` · ⊘ not compatible` (Yellow) when the skill is not compatible with that agent and the status is not already `incompatible`; line 2 (indented) the installed path, or, when nothing is installed there, the path it would install to followed by ` (not installed)`, all in Overlay
  5. blank line, then `FILES (N)` and a tree of the skill's files using the hashing walk (§4: no dot-paths, no symlinks): a root `SKILL.md` first, then directories as `name/` before files, each sorted by name, drawn like `tree(1)`: connectors `├── `, `└── ` and continuation `│   ` / `    ` (ascii icon set: `|-- `, `` `-- ``, `|   `), connectors in Overlay; each file shows the exec glyph (§9.5) if executable and a right-aligned human size (`B`, `KiB`, `MiB`, one decimal above 1 KiB). Files come from the vault copy; if the skill isn't in the vault, from the cursor agent's installed copy, titled `FILES (N, installed in <agent>)`; if neither exists, `no files`.
- Narrow terminals (< 70 cols): sidebar stacked above details, both full width.
- All widths via `lipgloss.Width`; long values truncated with `…`; nothing exceeds the terminal.
- Keys: `i` install, `u` uninstall, `U` update, `d` diff (pager), `a` adopt (only on `unmanaged`), `A` install into all configured agents (incompatible ones skipped and reported), `c` toggle compatibility of the marked agents, or the cursor agent if none marked (vault skills only; all agents compatible again = table deleted), `x` export (path prompt, default name per §7), `D` remove from vault (confirm; force confirm if installed anywhere), `esc` back, `?` help, `q` quit.
- Rows for skills not in the vault (orphaned/unmanaged/missing only) still open; actions that need the vault are disabled with an error notification.

### 9.4 Dialogs and modes

**Confirmations are modal**: every y/n confirm (plain, force, remove, discard, install-all) keeps the current screen visible but dimmed (all text re-colored to Overlay, styles stripped), and draws a small rounded-border box centered over it: title in the top border (` Uninstall `, ` Force uninstall `…), the question, the detail lines (path, reason, what is lost), and `y yes · n no` in hint style. Box width = widest line + padding, at least 40, at most terminal − 4. Border Accent for plain confirms, Red for force confirms. Notifications still draw on top.

**Screens with a title band.** Every non-main screen (ADD, ADOPT, NEW, IMPORT and its picker/list/fix-up steps, EXPORT, THEME, LOG, HELP) draws, under the header rule, a band exactly like the grid's column-header band: one centered title row (Text, bold) and a full-width rule (Overlay). Titles: `Add a skill to the vault`, `Adopt unmanaged skills into the vault`, `Create a new skill`, `Import skills` (`Import skills · choose a file`, `· pick skills`, `· fix <name>` for the steps), `Export <skill>`, `Theme`, `Log`, `Help`. One shared helper draws the band and centers the content block for every screen. The content renders as one horizontally centered block of the **same width on every titled screen and every step**: two thirds of the terminal width, at least 60, at most the terminal width. Content is left-aligned inside the block, so all titled screens share one left edge; inputs fill the block; long values truncated with `…`.

- `ADD` (key `n` on the main screen): three choices, one per row, left-aligned in the block like every titled screen: `c  Create   write a new skill (wizard)`, `i  Import   from a folder, file, git or URL`, `a  Adopt    N unmanaged skills in your agents` (N live = the number of unmanaged copies ADOPT lists, singular `skill` at 1; the row is dimmed and not selectable when N = 0, showing `no unmanaged skills`). `↑↓` + `enter` or the letter opens NEW, IMPORT or ADOPT; `esc` back. `esc` in those screens returns to the main screen.
- `ADOPT`: every `unmanaged` (skill, agent, path) across configured agents, grouped under an agent heading per configured agent (agent order; agents with none omitted). A filter row at the top, `All · claude · cursor · …`, switched with `tab`/`shift+tab` or `←→`, limits the list to one agent. `space` marks a row; `enter` adopts the marked rows, or the cursor row if none marked (force confirm on `ErrNeedsForce`). A name unmanaged in several agents with **different** hashes shows a `conflict` tag on each of its rows; marking two rows of the same name is refused with an error notification (adopt one, then the others become `modified`/handled normally). Same name with identical hashes needs one adopt (§7 adopt). Results as one notification summarizing the count. `esc` back.
- `NEW`: a wizard by default, `tab` switches to paste mode (the old textarea) and back. Wizard fields, moved through with `↑↓`/`enter`: name (live-validated against §3 rule 5 and existing vault names), description (live count `N/1024`), compatible agents (checkbox list of configured agents, all checked by default; all checked = no compat table). `ctrl+s` creates via the same op as `new --name` (§7.2); then a modal confirm `Open <path> in <editor>?`; `y` runs the editor with `tea.ExecProcess` and refreshes on return. Paste mode: multi-line textarea, live validation line, `ctrl+s` saves via `ops.Create`. `esc` cancels (confirm if anything was typed).
- `IMPORT`: a single source input (path or URL, §7.1). `ctrl+o` opens a file picker over the body starting at the input's directory (or the home dir): `↑↓` move, `enter` on a directory enters it, `backspace` goes up, `space` chooses the highlighted entry (directory, `.md`, `.tar.gz`/`.tgz`; other files are listed dimmed and not choosable), `.` toggles dot-entries, `esc` closes; choosing fills the input. `enter` on the input resolves the source: if several skills are found, a multi-select list (`space` marks, `a` marks all, `enter` imports the marked; none marked = refused with a hint); if a skill needs `--fix`, a fix-up form shows the problems and editable name (prefilled with the frontmatter name if valid, else the normalized hint) and description fields, `ctrl+s` imports with the fix. Name exists → force confirm. Results as notifications.
- `EXPORT`: single-line path input with default; `enter` runs; results as notifications.
- `THEME`: list of themes; moving the cursor previews live; `enter` keeps it for this session, `esc` restores the previous one. Never writes the config file.
- `HELP`: keys for the current screen + icon/status legend; scrolls with `↑↓`/`pgup`/`pgdn` when taller than the body.

### 9.6 Notifications

- Every action result, error and info message (install, diff refusal, refresh, theme kept, export written, …) becomes a notification: `kind` (success | error | info), title (short: the op, e.g. `installed`, `error`), message, timestamp.
- Shown as a stack of rounded-border boxes in the bottom-right corner of the body, directly above the bar, 1-col right margin, drawn over the body. Box width = min(48, terminal width / 2), at least 24; message wrapped inside, max 4 lines (`…` when cut). Top border carries ` <icon> <title> ` (icon = synced icon for success, invalid icon for error, info icon); border + title colored Green / Red / Accent.
- At most 3 visible; newest at the bottom; older ones drop off the top. Success/info expire after 4s, errors after 10s (driven by `tea.Tick`, testable with an injectable clock).
- `L` (on every screen, outside text inputs) opens `LOG` mode: a centered dialog (§9.4 rules) listing every notification this session, oldest first, `HH:MM:SS <icon> <title>: <message>`, scrollable, max 200 kept. `esc` closes.
- Notifications never write to disk.

## 11. Skill tarballs

- gzip-compressed tar. Top-level entries are skill folders `<name>/…`; one archive may hold several skills. Nothing else at top level (a `sapato-export.json` manifest with `{"format":1,"skills":{name:hash},"compatible":{name:[agents]}}` is written on export — `compatible` holds only skills with a compat table and is omitted when empty — and the manifest is ignored on import if absent).
- Export: files per hashing rules (§4: no dot-paths, no symlinks), modes preserved (0755 for exec, 0644 otherwise), dirs 0755, deterministic order, mtime zero.
- Import safety: reject absolute paths, `..` components, symlinks/hardlinks/devices, entries outside a top-level skill folder, total uncompressed size > 50 MiB, > 10k entries. Extract to a temp dir, validate every skill (when the TUI imports a picked subset, §9.4, only the picked skills must be valid; the manifest is still checked in full), then copy all-or-nothing into the vault (existing names refused unless `--force`; `--name` only allowed for single-skill archives).
